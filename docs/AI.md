# AI Assist

## Status: architecture only, deliberately

> Per the project brief, AI Assist is **designed and prepared but not implemented** at this stage.
> The interfaces, database schema, permission model and UI are all in place and ready for a
> provider. **No real model or API call is implemented or tested.** This is an intentional
> deferral to a later phase, not an unfinished feature.

The default is `AI_PROVIDER=disabled`, and with it every AI endpoint returns:

```json
{
  "available": false,
  "provider": "disabled",
  "reason": "AI Assist is not enabled. Model integration is deliberately deferred to a later
             phase; the interfaces, schema and UI are in place and ready for a provider."
}
```

Nothing fabricates tutoring content. There is no placeholder text presented as an AI answer, and
no button that appears to work and does not.

## What exists

### The provider interface

`services/api/app/services/ai_provider.py`

```python
class AIProvider(ABC):
    @property
    @abstractmethod
    def is_available(self) -> bool: ...

    @abstractmethod
    def complete(self, request: AIRequest) -> AIResult: ...

    # The four planned features, each delegating to complete() so a future provider
    # implements one method rather than five.
    def tutor_hint(self, *, question_prompt, student_answer, skill_name) -> AIResult: ...
    def explain_mistake(self, *, question_prompt, student_answer, correct_answer) -> AIResult: ...
    def generate_questions(self, *, skill_name, grade, difficulty, count, question_type) -> AIResult: ...
    def summarise_progress(self, *, student_name, summary) -> AIResult: ...
```

Two implementations ship:

- **`DisabledProvider`** (default) — reports unavailability with a clear reason.
- **`EchoProvider`** — a deterministic offline stand-in used to exercise the plumbing (request
  logging, review gating, error handling) without network access. It returns an obviously-templated
  string prefixed `[ECHO STUB — not generated by a language model]`, so nothing it emits could be
  mistaken for real tutoring content. **It is not an AI and never claims to be.**

An unknown `AI_PROVIDER` value resolves to `DisabledProvider` rather than raising: a typo in an
environment variable should degrade the AI feature, not take down the API.

### Audit schema

Two tables, populated on **every** invocation including refusals:

**`ai_interactions`** — user, student, feature, provider, model, request context, prompt, response,
status, error, latency, token counts, and `reviewed_by_id` / `reviewed_at` for human review.

**`ai_generation_batches`** — a teacher's request for N draft questions: skill, grade, difficulty,
type, counts requested/generated/approved, and `requires_human_approval`.

Auditability matters more than usual here. An AI tutor talking to twelve-year-olds needs a
reviewable transcript, and an AI-generated question must be traceable to the prompt that produced
it. Building the audit trail *after* wiring up a provider would mean the first weeks of use are
unauditable — so it exists first.

### API surface

| Endpoint | Access | Purpose |
|---|---|---|
| `GET /ai/status` | public | What is configured and which features would be available |
| `POST /ai/tutor-hint` | authenticated | A Socratic nudge that guides without revealing the answer |
| `POST /ai/explain-mistake` | authenticated | Explain why a specific answer was wrong |
| `POST /ai/generate-questions` | teacher | Draft questions for review |
| `GET /ai/batches` | teacher | Generation history |
| `GET /ai/pending-questions` | teacher | AI drafts awaiting approval |

### The human-approval gate

AI-generated questions land in `questions` with `status = pending_review` and
`generated_by_ai = True`.

**This gate is enforced by the query filters, not by convention.** `_candidate_questions()` in
`app/services/practice.py` filters on `status == PUBLISHED`, so an unapproved question is
structurally unable to reach a student even if some other code path forgot to check. A teacher must
explicitly publish it via `POST /teacher/questions/{id}/publish`, which re-validates the template
before allowing it.

### Frontend

`GET /ai/status` drives the UI. When disabled, AI features render an honest "prepared but not
enabled" state rather than being hidden — so the capability is visible as planned work rather than
appearing to not exist.

## What a later phase must build

Wiring a provider is the small part. These are the parts that actually matter:

1. **A provider implementation.** Roughly 50 lines against any modern API — the interface is
   already shaped for it.
2. **Prompt templates tuned for pedagogy.** A tutor hint must guide without revealing. That is a
   genuinely hard prompt-engineering problem and the difference between a useful feature and one
   that teaches students to fish for answers.
3. **Safety filtering on output before a minor sees it.** Non-negotiable. Model output must be
   moderated before it reaches a student, and the `reviewed_by_id` column exists for the cases
   where a human should be in the loop.
4. **Cost controls and rate limiting.** Per-user and per-day caps. Redis is already available.
5. **Evaluation.** Generated questions need checking for mathematical correctness — the exercise
   engine's validator is a start, but a question can generate cleanly and still be pedagogically
   wrong or mis-levelled for the grade.
6. **A privacy decision.** Sending student work to a third-party model is a data-protection
   question, especially for minors. It needs a policy and, plausibly, parental consent before it
   ships.

## Design principles

**Never couple to one provider.** Everything goes through `AIProvider`. Swapping providers, or
running several, is a configuration change.

**Never let AI output reach a student unreviewed.** Enforced structurally, as above.

**Log everything.** Including refusals. A feature you cannot audit is a feature you cannot debug or
defend.

**Fail honestly.** When AI is unavailable the user is told so plainly. A feature that silently
degrades into something worse is more damaging than one that is clearly switched off.

**AI assists, it does not teach.** The mastery model, the recommendations and the grading are all
deterministic and explainable. If AI were removed tomorrow the platform would lose a convenience,
not its core function. That is deliberate: a tutoring platform whose pedagogy depends on an opaque
model is one nobody can reason about — including the teachers using it.
